01 / 12 the two hard problems

Rename identity, and merging operations — not text.

A schema tool can't diff bytes. It has to know that a column renamed on one branch and retyped on another is the same column, and it has to reason about drop/add/alter operations, not lines of SQL.

Problem 1 — identity. Postgres reuses internal ids; there's no catalog fact that says "this column is that column" once it's renamed on one branch.
Fix. A synthetic UUID assigned once, at creation — never recomputed, never derived from a name.
Problem 2 — merge. Two branches each mutate a schema independently. Comparing SQL text tells you nothing about intent.
Fix. A DAG of operations (git-commit-style), and a classifier that reasons over the operations themselves.
02 / 12 phase 1 — authoring

Every change starts as a real CLI verb.

No hidden state. Create a table, add a column, branch, rename a column and retype it in the same breath — each one an explicit, typed operation appended to the DAG.

03 / 12 two-way sync

Every migration rewrites a plain .schema file.

Rails schema.rb-style. Human-readable, always current, and — in Phase 2 — the same file a human can edit directly.

schemas/main.schema
table users { column contact_email: text}
Kept in schemas/ — visible, not buried under .schemavcs/ — specifically so a human can open and edit it.
04 / 12 merge — real conflict

Same column, two branches, two different answers.

Branch-a renames x → y. Branch-b, independently, renames the same x → z. Same underlying id — no way to auto-merge "call it y" with "call it z."

walkthrough 02 — merge conflict
$ schemavcs merge branch-b --into branch-aConflict on identity 42a18536…: both branches set a different nameKeep [a]/[b]/[both]? amerged 'branch-b' into 'branch-a' at 0c518cae5943 (1 conflict(s) resolved)
Structural guardrail: a HumanConfirmationToken is the only thing that can commit a conflict resolution — and it's one-shot. No silent auto-merge, ever.
05 / 12 the quiet cases

Most merges need no human at all.

Same change on both sides, or two different, non-overlapping fields of the same column — both resolve automatically. This is most of what actually happens in practice.

IDENTICAL
both branches: nullable -> False$ schemavcs merge branch-b --into branch-amerged 'branch-b' into 'branch-a' (0 conflict(s) resolved)
COMMUTING
a: rename bio -> biographyb: bio nullable -> False$ schemavcs merge branch-b --into branch-amerged (0 conflict(s) resolved)
Both operations survive. Neither contradicts the other — nothing to ask.
06 / 12 cross-object pass

Drop a table. Something else still points at it.

Branch-a drops orders entirely. Branch-b, independently, adds a column to it. Different ids — the per-identity classifier never even sees this pair. A separate pass walks every reference and checks it against what the other branch destroyed.

walkthrough 04 — cross-object conflict
$ schemavcs merge branch-b --into branch-aConflict: branch A dropped table 'orders' that another branch's operation still referencesThe dropped table/column wins; the dependent object will also be dropped. Press enter to acknowledge.merged (1 conflict(s) resolved)
Only one resolution is offered — the drop wins. Undoing a drop would mean resurrecting an object from nothing; this tool keeps no copy of what it destroyed.
07 / 12 single-valued conflicts

A type can't be two things. Neither can a boolean.

Both branches retype the same column differently, or set its nullability differently. A real, found-and-fixed CLI detail: the prompt used to offer a meaningless "both" for these — now it doesn't.

walkthrough 11 — type vs type
$ schemavcs merge branch-b --into branch-aConflict on identity edb3e2cf…: both branches set a different typeKeep [a]/[b]? amerged (1 conflict(s) resolved)
No [both] option — a column has exactly one type. Offering it used to silently mean "whichever replays last wins," dressed up as a real choice.
08 / 12 name collisions

Two branches, two different columns, one name.

Both branches add a column called notes — different underlying ids, same name. Not a same-identity conflict, but still invalid DDL if both survive. Resolved by DAG distance from the merge base, not by wall-clock time.

walkthrough 03 — name collision

09 / 12 phase 2 — the second path

Or: just edit the file by hand.

Rename a column in the .schema file directly, no CLI verb. sync diffs the edit against the tracked snapshot and has to guess what happened — similarity-scored, human-confirmed, never silent.

10 / 12 the guessing has limits

Guessing wrong is worse than not guessing.

score = 0.45·name + 0.25·type + 0.15·constraints + 0.15·position — only proposed when both sides prefer each other, with a real gap over the runner-up. A split column correctly gets no proposal at all.

11 / 12 full pipeline

Detected. Merged. Emitted. One engine.

A rename detected on branch-a merges against changes authored directly on branch-b, through the exact same merge and DDL code Phase 1 already proved — zero changes to either.
